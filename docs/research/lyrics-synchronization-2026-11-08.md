# Синхронизация лирики: текущее состояние и варианты улучшения

Проверка от 8 ноября 2026 года. Код просмотрен на базе `5ab3e61`. Ниже отдельно отмечены действующее поведение, предложения и ограничения внешних проектов. Новые анализаторы в приложение в рамках исследования не встраивались.

## Что сейчас определяет конец строки

`src/features/lyrics/timingResolver.ts` применяет такой приоритет:

1. Явный конец строки из ручного редактирования или источника.
2. Известный конец последнего слова из расширенного LRC, если явного конца строки нет.
3. Сопоставленный конец фразы из глубокого анализа при достаточной уверенности.
4. Оценка по тексту и соседним началам строк.

Последний вариант не слушает аудио. Он считает слова и приблизительные слоги, учитывает пунктуацию и растянутые слова. При наличии нескольких подходящих соседних строк оценивает местный темп подачи. Длительность ограничивается следующей строкой и концом файла; короткие остаточные промежутки могут включаться в показ строки. BPM даёт только слабую поправку, а не определяет конец вокала.

Поэтому правильное начало строки само по себе не гарантирует правильный конец. Инструментальную паузу нельзя достоверно вывести из количества букв или BPM. Ручные и исходные точные окончания должны сохранять приоритет над автоматикой.

## Что делает глубокий анализ

Поток: `LyricsAnalysisBridge` → `lyricsAnalysisConnection` → `analysis/runner` → ASR worker → `lyricsService` → resolver. Он работает для синхронизированного текста с недостающими точными окончаниями.

- Модель — закреплённая `onnx-community/whisper-tiny_timestamped`, ONNX q8, один WASM-поток. Семь файлов manifest суммарно занимают примерно 43,6 МБ; revision и SHA-256 проверяются. Это модель распознавания речи, а не выделение вокала.
- Вход — зарегистрированный локальный или уже закэшированный аудиофайл. Для файла действуют ограничения размера/длительности и декодирования. Обычный незакэшированный поток не становится входом автоматически.
- Файл декодируется в mono PCM 16 кГц, но распознавание не является непрерывным полным сканированием всей песни. Планировщик выбирает небольшие окна рядом с предполагаемым концом текущей фразы. За затраченное время начисляется пауза перед следующей работой; после простоя освобождаются worker и PCM.
- Распознанные слова сопоставляются с окончанием известной строки. Результатом для playback становится уверенный конец фразы. Повторяющиеся или неверно распознанные слова могут не пройти сопоставление.
- Кэш хранит признаки аудио, фрагменты распознавания и сопоставленные окончания для конкретного источника лирики. Изменение файла, алгоритма или модели проверяется при повторном использовании.

Есть ещё важная защита в `playbackTiming.ts`: уже достигнутые сегменты текущего прохода фиксируются, чтобы уточнение не дёргало текст назад. Если анализ пришёл после начала строки, новое окончание может не примениться к ней до следующего прохода или перемотки. Это объясняет часть ощущения «анализ ничего не поменял». Выключение новых вычислений также не обязательно отменяет ранее сохранённый результат из кэша.

Ключевые файлы: `analysis/contract.ts`, `asr.worker.ts`, `runner.ts`, `matchWords.ts`, `src-tauri/src/lyric_analysis.rs`, `src-tauri/lyric_model_manifest.json`.

## Почему режим «по словам» пока приблизительный

Расширенный LRC может содержать времена слов, а ASR-фрагменты уже сохраняют timestamped words. Но `LyricSegment` не переносит эти данные в отрисовку. В `SyncedView` границы подсветки рассчитываются по измеренной ширине слов и доле заполнения всей строки (`wordFill.ts`).

То есть слово сейчас выделяется не потому, что именно его услышал анализатор. Большое слово получает большую часть времени; короткое — меньшую. Это плохо соответствует растянутым гласным, быстрой подаче, паузам между словами и каверам.

Первое полезное улучшение не требует новой модели: провести достоверные исходные word timings через resolver и сегменты в renderer. Нужны проверка диапазонов, сопоставление с отображаемыми словами и обработка одновременно поющихся строк. Если данные неполные или текст не совпадает, оставлять нынешнее заполнение резервным вариантом, а не выдавать его за точную синхронизацию.

## Уже имеющийся вариант без модели

`vocalActivity.ts` использует спектральную эвристику: голосовой диапазон 180–3600 Гц, распределение энергии, признаки формант/пиков и гистерезис при выделении участков. Сейчас она обслуживает явную кнопку коррекции в редакторе. Используется короткая недавняя история спектра рядом с выбранной строкой; это не автоматическое сканирование всей песни и не поиск текущего слова.

Гитара, синтезатор или другой инструмент могут дать похожие признаки. Поэтому сообщение об отсутствии ясной фразы не обязательно означает отсутствие вокала: эвристика могла не получить подходящее окно или достаточную уверенность.

Практичный следующий эксперимент без ML: анализировать доступный файл короткими фреймами в фоновом native/worker-процессе, сочетая гармоничность, изменение спектра, несколько голосовых полос и адаптивный фон. Искать вероятные вокальные хвосты только рядом с уже известными таймингами. Хранить уверенность, не править вручную заданные границы и не превращать каждый межсловный вдох в отдельную строку паузы. Это предложение, его качество на музыке ещё не измерено.

Только экспериментальная база без нейросетевого ASR, не готовое решение для пения. |

Само по себе обнаружение вокала не определяет, какое слово поётся. Для этого нужно сопоставить известный текст с аудио или получить тайминги из источника. Перенос ASR-timestamps без проверки текста также может подсветить не то слово.

## Рекомендуемый порядок

1. Использовать уже доступные исходные word timings в режиме по словам; резервное заполнение оставить для остальных строк. Это не требует загрузки новой модели.
2. Сделать отдельный экспериментальный проход DSP по доступному файлу для уточнения начала/конца фраз заранее. Не менять подтверждённые ручные тайминги; ограничить конкурентность и нагрузку, сохранять результаты по fingerprint файла. Отдельно проверить политику поздних уточнений: не откатывать уже заполненные слова, а слишком поздние изменения оставлять на следующий проход.
3. Сравнить простой DSP с малым AED на наборе реальной русской музыки, включая тихий вокал, рэп, каверы, sped-up/slowed, плотную гитару и длинные инструментальные вступления. Измерять ошибки границ и ложные паузы, а не только скорость обработки.
4. Для отсутствующих word timings добавить выравнивание известной лирики с аудио и ручную проверку/коррекцию. Для русского нельзя обещать результат от aligner, который этот язык не поддерживает. Без надёжного выравнивания лучше показывать честную приблизительную подсветку.

Ни один из найденных проектов не подтверждает универсальное точное определение текущего слова в произвольной песне одним лёгким DSP-детектором без языкового/акустического выравнивания.

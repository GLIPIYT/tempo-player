# Tempo: предложения к визуальной полировке

Дата: 01.10.2026. Этот документ описывает следующий этап; изменения поведения плеера здесь **не реализованы**. Основание — текущие исходники в `main`, HTTP-запросы к публичному TheAudioDB и первичная документация. Ручные проверки интерфейса оставлены пользователю.

## Автоматические портреты исполнителей

**Что подтверждено.** В `src-tauri/src/theaudiodb.rs:9` уже указан бесплатный ключ `123`, а запросы идут из Rust, не из WebView. Сейчас поиск запускается вручную из `src/pages/ArtistDetailPage.tsx:77`, сохранение — отдельным действием. Автоматической очереди заполнения нет.

Запрос `https://www.theaudiodb.com/api/v1/json/123/search.php?s=coldplay` с текущим Tempo User-Agent во время исследования вернул HTTP **200** и JSON артиста Coldplay. Вариант ключа `2` вернул **404**. Поэтому сообщённый пользователем **403** пока не воспроизведён: причина не установлена, менять `123` на `2` нельзя считать исправлением.

Официальная документация подтверждает бесплатный ключ `123`, максимум один результат поиска исполнителя и 30 запросов в минуту; превышение лимита обозначается 429. Условия отдельно ограничивают распространение в магазинах приложений. Документация не уточняет, привязан ли лимит к IP или общему ключу. [API TheAudioDB](https://www.theaudiodb.com/free_music_api), [условия](https://www.theaudiodb.com/docs_terms_of_use.php).

**Предлагаемое поведение.** При запуске и после появления новых исполнителей поставить в фоновую очередь только записи без портрета. Приоритет — видимые карточки, затем любимые/часто слушаемые, затем остальные. Одна загрузка поиска за раз, не чаще одного запроса в три секунды; ручные запросы должны пользоваться тем же лимитером. Сохранять результат автоматически только при точном совпадении нормализованного имени и отсутствии неоднозначности. Не удалять части имени, `feat.` и состав группы для получения искусственного совпадения. Перед записью повторно проверить, что пользователь ещё не задал картинку.

Хранить источник, внешний ID, статус и время следующей попытки. «Не найдено» кешировать на 7 дней; 429 — ожидание сервиса/не менее минуты, 403 — остановка этого провайдера и более длинная задержка, а не бесконечные запросы. Успешный файл хранить локально и переиспользовать. Для диагностики записывать HTTP-код и Content-Type без секретов; 403 может происходить на поиске или при скачивании картинки, эти стадии надо различать.

**Резервный путь.** MusicBrainz нужен для установления личности исполнителя, затем его Wikidata-связь → свойство изображения P18 → файл Wikimedia Commons. Это несколько запросов, поэтому резервный путь медленнее и покрытие не гарантировано. MusicBrainz требует не более одного запроса в секунду и корректный User-Agent; публичные чтения доступны без входа. Wikidata предоставляет JSON известных сущностей, Commons Imageinfo — URL миниатюры и метаданные изображения. Для неоднозначного имени автоматически не выбирать первый результат; оставить силуэт и ручной выбор. [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API), [Wikidata: доступ к данным](https://www.wikidata.org/wiki/Wikidata:Data_access), [Commons Imageinfo](https://www.mediawiki.org/wiki/API:Imageinfo).

Сведения об авторе и лицензии Commons сохранять с файлом и показывать в компактном пункте «Источник изображения». Для уже надёжно связанного с SoundCloud исполнителя можно использовать аватар его профиля, не выдавая найденный по одному имени чужой профиль за точное совпадение.

## Короткие треки и fade

**Что видно в коде.** `src/player/controller.ts:657` запускает переход, как только `duration - position <= crossfadeSeconds()`. Здесь нет ограничения относительно длины текущего/следующего трека; оставшееся время в секундах файла сравнивается с длительностью анимации. `src/player/engine.ts:348` выполняет fade по реальному времени `performance.now()`.

Следовательно, при fade 5 секунд трек длиной 3 секунды подходит под условие почти сразу. Во время перехода очередь уже продвигается (`controller.ts:682`), а флаг `crossfading` сбрасывается после запуска перехода, раньше окончания самого fade. Следующий короткий трек может инициировать новый переход и уничтожить предыдущее затухание (`engine.ts:317`, `detachFade`). Это подтверждённое объяснение возможного поведения по коду; конкретный пользовательский сценарий вручную не воспроизводился.

**Предложение.** Разделить два режима: crossfade между песнями и короткую защиту от щелчка. Для звуков короче 8 секунд отключать перекрытие треков; оставить очень короткую огибающую 10–20 мс. Для остальных ограничивать реальную длительность перехода:

`F = min(пользовательский fade, 0.2 × Dтекущий / скорость, 0.2 × Dследующий / скорость)`.

Если длительность неизвестна или следующий источник не подготовлен, запускать обычную смену. Сначала подготовить следующий источник без продвижения очереди, повторно проверить актуальность запроса и остаток текущего трека; затем атомарно переключить очередь. Сравнивать `remaining / playbackRate` с F, держать признак активного перехода до его окончания, отменять подготовку при ручной смене. Историю завершения фиксировать один раз, а не заранее после первой попытки перехода.

Порог 8 секунд и доля 20% — предложенные параметры, их можно скорректировать после прослушивания коротких звуков пользователем.

## Настоящий спектр стриминга и смена на кеш

**Текущее состояние.** `src/player/controller.ts:488` направляет кеш и SoundCloud HLS в канал `local`, то есть в Web Audio graph. Progressive SoundCloud URL идёт в `stream` и обходит graph. Это защищает звук от ситуации, когда браузер разрешает воспроизведение, но запрещает анализ. Стандарт прямо требует тишину на выходе MediaElementAudioSourceNode для ресурсов без нужного CORS-доступа. Простой вызов `createMediaElementSource` или добавление `crossOrigin` эту проблему не решает. [Web Audio: CORS](https://www.w3.org/TR/webaudio-1.0/#MediaElementAudioSourceNode-security).

YouTube в текущем коде (`controller.ts:491`) сначала скачивается через yt-dlp, затем играет локально. Поэтому здесь отдельного канала живого YouTube-стриминга пока нет; спектр должен быть доступен после начала локального воспроизведения.

**Первый практический этап — смена на готовый файл.** SoundCloud уже скачивает progressive файл в фоне (`src-tauri/src/soundcloud_store.rs:170`) и отправляет `library://changed` после завершения (`:106`). Добавить событие готовности именно аудиофайла с идентичностью провайдера, ID и локальным путём; событие обновления медиатеки само по себе не является контрактом аудиопереключения.

Движок готовит второй элемент с локальным файлом без остановки текущего, сохраняет скорость, preservesPitch, громкость, EQ и нормализацию. После `loadedmetadata`/готовности выставляет позицию, пересчитанную с учётом времени подготовки, дожидается seek и сравнивает позиции двух элементов. Затем короткое линейное перекрытие 30–60 мс и отключение старого источника. Для одинакового коррелированного аудио линейная огибающая предпочтительнее equal-power: последняя способна поднять уровень в середине перекрытия.

Это не новая песня: не менять очередь, не обнулять позицию, не писать ещё одно прослушивание, не перезапускать лирику/Discord. Все async-операции привязать к поколению воспроизведения. На паузе заменить источник без воспроизведения. Если seek/длительность/источник не совпали, пользователь перемотал, идёт crossfade или до конца осталось мало времени — оставить действующий stream до конца. Абсолютно незаметный переход требует проверки на реальных файлах: контейнер/encoder delay и сетевые источники могут различаться.

**Второй этап, если нужен спектр с первых секунд progressive stream.** Rust-прокси с узким контрактом «провайдер + ID», потоковой передачей, поддержкой Range и корректным Content-Type предоставляет WebView локально доступное аудио. Не передавать произвольный внешний URL из UI. Сохранять байты на диск потоково, отменять устаревшие запросы, не держать всю песню в RAM. Потребуется отдельная работа с Tauri-протоколом и WebView2; это более объёмная задача, чем hot swap, и её работоспособность здесь не подтверждалась.

## Предзагрузка следующих четырёх треков

Сейчас `preloadNext` (`src/player/controller.ts:638`) работает только при включённом `cacheBeforePlay`, выбирает один следующий трек и только SoundCloud. `soundcloud_store.rs:209` явно отказывает в кешировании HLS. `download_to_cache` (`:370`) сначала принимает весь ответ в память, затем пишет общий `.tmp`; dedup и отдельного глобального лимитера в этом пути нет.

**Предложение.** Поддерживать скользящее окно из четырёх следующих доступных некешированных треков в фактическом порядке очереди, включая shuffle/repeat-all. Четыре цели не означают четыре одновременные загрузки: стартовый лимит — 1 фоновая загрузка, приоритет текущему треку. Общий scheduler должен обслуживать воспроизведение, prefetch и ручное кеширование, дедуплицировать по `(provider,id)` и разделять готовый результат между потребителями.

Пересчитывать окно после смены очереди, shuffle, next, move/remove и ручного запуска. Не зацикливаться при repeat-one, не выходить за уникальные доступные элементы. Старые не начатые задачи удалять; текущую загрузку можно закончить и сохранить, если её безопасное прерывание пока не реализовано. Сохранять успешные файлы и retry только для временных ошибок с задержкой; HLS пропускать до отдельного механизма сохранения. YouTube включить тем же scheduler через уже существующий yt-dlp cache с низким лимитом процессов.

Перед увеличением окна перевести download на запись чанков в уникальный временный файл и atomic rename, добавить общий in-flight registry и защитить текущий/следующие подготовленные файлы от удаления лимитером кеша. Иначе prefetch может конкурировать с проигрыванием за `.tmp` и память, а лимит кеша — удалить только что подготовленный файл. При маленьком лимите/недостатке диска показывать фактическое число подготовленных треков, не обещать всегда четыре.

## Создание исполнителя/альбома из редактора тегов

Сейчас `src/components/common/TrackMetadataEditor.tsx:422` использует обычные `<select>` существующих ID. `TrackMetadataEditRequest` в `src-tauri/src/models.rs:96` не содержит нового имени исполнителя/альбома. Команда (`commands.rs:706`, `:738`) строит записываемые названия из выбранных сущностей. Поэтому создание требует дополнения контракта, одного изменения UI недостаточно.

При этом `database.rs:1478` уже умеет разрешать сущности по названиям в транзакции завершения редакции, а `get_or_create_artist`/`get_or_create_album` (`:4093`, `:4112`) существуют. Их стоит переиспользовать вместе с текущим журналом восстановления файла.

**Предложение интерфейса.** Компактный combobox: поиск, результаты, последняя строка «Создать «Имя»». Новое имя остаётся черновиком до «Сохранить», а не сразу создаёт пустую сущность в БД. Альбом всегда связан с выбранным album artist; одинаковые названия у разных исполнителей не объединять. Удаление выбора и очистка названия должны быть явными. Клавиатура: стрелки, Enter, Escape; ограниченная высота списка, единая типографика с другими dropdown.

**Backend.** Передавать взаимоисключающие варианты Existing ID / New name / None, валидировать непустое имя и длину. Проверять существование выбранных ID перед staging и после сохранения. Записать новые названия в файл; создать/сопоставить сущности при успешном завершении той же транзакции DB+journal, включая artist/album entity override. При ошибке не оставлять пустые артистов/альбомы. Исходные метаданные и откат должны продолжать работать.

## Подборки: конкретные варианты и алгоритмы

**Уже доступные данные.** `Track` содержит play/skip count, lastPlayedAt, addedAt, duration, genre, album/artist. `listening_history` содержит дату, listened_sec, completed/skipped (`database.rs:181`, `:2993`); есть отдельный плейлист лайков. `get_hour_picks` (`:2077`) считает историю около текущего часа ±1 час; `buildHourMixes` (`src/utils/hourMixes.ts:20`) сейчас создаёт общую подборку и до трёх миксов исполнителей. Метаданные эмоциональной окраски, тональности и энергии всех песен **не существуют**. BPM из локального анализа тоже не гарантирован для всей библиотеки.

Предлагаемые подборки Tempo:

| Подборка | Кандидаты и ранжирование |
| --- | --- |
| На повторе | Любимые треки последних 14 дней: completed/listened share, убывающий вес по возрасту прослушивания, штраф ранним скипам. |
| Новое для вас | Добавлены за 30 дней, мало прослушиваний; повысить связанные с любимыми артистами/жанрами, не включать уже часто прослушанные. |
| Забытые любимые | Минимум 3 качественных прослушивания или лайк, нет запуска 30 дней; баланс прежнего интереса и давности. |
| Без пропусков | Треки с хотя бы 5 наблюдениями и высоким сглаженным completion rate, а не 100% после единственного запуска. |
| Утро / Вечер / Выходные | История в соответствующих локальных часах/днях недели с большими весами последним 60–90 дням. При недостатке истории блок скрыт. |
| Любимый исполнитель: глубже | Сначала ранее мало слушанные песни артиста, затем устойчиво любимые; отделить от простого top artist. |
| По жанру | Реальные genre tags и совместное присутствие в пользовательских плейлистах, без распознавания жанра по обложке/названию. Название UI — сам жанр. |
| Дальше по темпу | Близкий BPM к текущей песне, только когда анализ имеется; учитывать half/double-time неоднозначность и отмечать неподготовленный набор. |
| Волна от трека | SoundCloud related/station кандидаты плюс локальные совпадения, с фильтрацией дублей. Это внешнее радио от seed, а не персональные рекомендации аккаунта. |

Все эти алгоритмы — предложения, не описание уже работающей функции. Общая база рейтинга: `log1p(качественные_прослушивания) + бонус_лайку - сглаженный_штраф_ранним_скипам`; историю взвешивать экспоненциально по давности. Play count сейчас повышается при запуске (`controller.ts:627`), поэтому нельзя считать его полноценным прослушиванием. Ранний skip считать по доле длительности и минимальному количеству наблюдений; звуки в несколько секунд отделять от музыкальных рекомендаций.

Стабилизировать подборки на день/час, хранить seed и snapshot ID, не пересортировывать после каждого клика/лайка. Добавить разнообразие: не более двух треков одного артиста подряд, не более 20–25% одного артиста в общем миксе, исключать недавно скипнутые. При малой медиатеке ослаблять правила явно и не показывать несколько почти одинаковых подборок. Для сессии: примерно 70% знакомого, 20% мало слушанного из медиатеки, 10% внешних кандидатов — только когда внешний источник включён.

**Starroad.** Публичный музыкальный плеер с этим точным названием не удалось надёжно идентифицировать через GitHub и веб-поиск. Найденные совпадения относятся к другим продуктам. Поэтому ни одна строка таблицы не обозначена как «подборка из Starroad». Нужна ссылка или скрин его подборок, чтобы перенести именно существующие категории и сравнить поведение.

## Порядок реализации после выбора превью

1. Общие размеры controls и dropdown, убрать Discord Application ID из UI, уменьшить мини-плеер, убрать повторный Tempo над навигацией; адаптивный контраст поверх обоев.
2. Ограничение fade для коротких треков и единый безопасный cache scheduler, затем окно prefetch 4.
3. Автоматические портреты с rate limit/backoff, создание сущностей в редакторе.
4. Hot swap без перезапуска истории/лирики и отдельная работа над progressive streaming graph.
5. Новые устойчивые подборки, затем BPM/внешняя волна по реально доступным данным.

Для ручной проверки будущей реализации: 3-секундные звуки с fade 5–10с и repeat-one; speed 0.5/2×; смена очереди при prefetch; кеш с маленьким лимитом; потеря сети; hot swap при паузе/seek/на хвосте трека; одноимённые исполнители и альбомы; портреты с 403/429; пустая/маленькая история рекомендаций. Эти проверки пока не проводились.
